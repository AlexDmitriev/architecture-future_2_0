# План управления рисками трансформации «Будущее 2.0»

План привязан к [карте рисков](risk-map.md) и трёх этапной дорожной карте (0–6, 6–18, 18–36 месяцев).

---

## Принципы управления

1. **Risk-based delivery** — каждый этап миграции имеет критерии выхода (exit criteria) по рискам.
2. **Dual-run и обратимость** — критичные системы переключаются поэтапно, с возможностью отката.
3. **Разделение ответственности** — технические меры для платформы, управленческие — для людей и процессов.
4. **Прозрачность** — единый реестр рисков, ежемесячный review на Architecture Board.

## Меры по снижению рисков

### Архитектурные риски

| ID | Меры снижения | Тип |
|----|---------------|-----|
| **A1** Расползание доменов | Зафиксировать границы доменов в ADR. Запретить новую бизнес-логику в legacy DWH (policy as code в CI). Ввести доменные API и data products как единственный способ обмена. | Техническая + управленческая |
| **A2** Расхождение KPI | Единый Semantic Layer в витрине. Каталог метрик с владельцами. Контрактное тестирование data products между доменами. | Техническая |
| **A3** Затяжные мосты | Roadmap decommission для Camel/DWH с датами. KPI: % трафика через event mesh. Anti-Corruption Layer с ограниченным сроком жизни (TTL). | Управленческая + техническая |
| **A4** PHI/PCI в аналитике | PHI Filter на уровне компонента витрины. Data classification tags. Автоматические сканы PII/PHI в pipeline. Региональные политики хранения. | Техническая |
| **A5** Сложность streaming | Начать с 1–2 доменов (финрасчёты, пациентский поток). Capacity planning Kafka/Flink. SLA на lag витрин. | Техническая + управленческая |
| **A6** Vendor lock-in | Абстракция через K8s, open formats (Parquet, Avro), multi-cloud IaC (Terraform). | Техническая |

### Организационные риски

| ID | Меры снижения | Тип |
|----|----------------|-----|
| **O1** Сопротивление | Программа change management: пилотные клиники, champions, параллельная работа старого и нового UI 3–6 мес. Обучение операторов. | Управленческая |
| **O2** Нехватка компетенций | Hiring + аутстафф на этап 0–12 мес. Внутренние гильдии (Kafka, Data, Security). Партнёрство с облачным интегратором. | Управленческая |
| **O3** Нет data owners | Модель Data Mesh: назначить Domain Data Owner в каждом подразделении. RACI для витрин и событий. | Управленческая |
| **O4** Конфликт приоритетов | Portfolio board с представителями 4 подразделений. Общий backlog трансформации с квартальными OKR. | Управленческая |
| **O5** Партнёры | Partner Integration Hub с версионированными API. SLA на онбординг. Песочница для фармы и производителя оборудования. | Техническая + управленческая |
| **O6** Недоверие к отчётам | Параллельная сверка отчётов (old BI vs new portal) 2 квартала. Визуализация lineage в каталоге. | Управленческая + техническая |

### Технологические риски

| ID | Меры снижения | Тип |
|----|----------------|-----|
| **T1** Миграция DWH | Инвентаризация stored procedures и ETL. CDC (Debezium) в event mesh. Strangler Fig: по одному предметному домену. Регрессионные тесты на выборках данных. | Техническая |
| **T2** Простои cutover | Blue/green или canary для клинического портала и финтех-сервисов. Окна обслуживания согласованы с клиниками. Runbook отката. | Техническая + управленческая |
| **T3** ИБ инциденты | Zero Trust IAM, RBAC/ABAC, MFA. Секреты в vault. Pen-test витрины до prod. Маскирование в логах. | Техническая |
| **T4** Нестабильность events | Schema Registry + compatibility checks. DLQ с алертами и replay. Idempotent consumers. Chaos-тесты на брокер. | Техническая |
| **T5** Производительность lakehouse | Tiered storage, партиционирование, pre-aggregated marts. Материализованные витрины для тяжёлых отчётов. | Техническая |
| **T6** Долг AI-сервисов | MLOps: versioning моделей, A/B, мониторинг drift. Отделить inference от training. Feature store. | Техническая |
| **T7** Регуляторика регионов | Data residency per region. Юридическая экспертиза до запуска. Локальные KMS и audit trail. | Управленческая + техническая |

## Распределение: технические vs управленческие меры

| Категория рисков | Преимущественно технические | Преимущественно управленческие | Комбинированные |
|------------------|----------------------------|-------------------------------|-----------------|
| Архитектурные | A2, A4, A6 | A3 (governance) | A1, A5 |
| Организационные | O5 (частично) | O1, O2, O3, O4, O6 | O5 |
| Технологические | T1, T3, T4, T5, T6 | T7 (legal) | T2, T7 |

**Вывод:** организационные риски (O1–O4, O6) почти полностью требуют управленческих мер; технологические (T1, T3–T6) — инженерных. Архитектурные и регуляторные риски (A1, A4, T7) снимаются только сочетанием обоих подходов.

## План по этапам трансформации

### Этап 1 (0–6 месяцев) — пилот

| Цель | Меры |
|------|------|
| Снизить T1, T4 | Пилот CDC из DWH + Kafka в домене финрасчётов или пациентского потока |
| Снизить O3 | Назначить data owners в пилотных доменах |
| Снизить A4 | Политика «no PHI in витрина» + PHI Filter в дизайне |
| Снизить O2 | Обучение 2 команд: streaming + Terraform/IaC |

**Exit criteria:** пилотные события в prod-like среде, DLQ работает, ADR по доменам согласованы.

### Этап 2 (6–18 месяцев) — масштабирование

| Цель | Меры |
|------|------|
| Снизить A3 | ACL для Camel, план вывода 50% интеграций с ESB |
| Снизить A2 | Semantic Layer v1, каталог метрик |
| Снизить O1, O6 | Запуск self-service портала, параллельная сверка с Power BI |
| Снизить T6 | MLOps для 1–2 AI-сервисов |

**Exit criteria:** портал в prod, ≥50% доменных интеграций через events, legacy DWH только read-only.

### Этап 3 (18–36 месяцев) — целевое состояние

| Цель | Меры |
|------|------|
| Снизить A1, A3 | Decommission Camel bridges и SQL Server DWH |
| Снизить T7 | Развёртывание в 2–3 регионах с data residency |
| Снизить A5 | Near-real-time витрины для ключевых KPI |
| Снизить O5 | Онбординг фармы и производителя оборудования через Partner Hub |

**Exit criteria:** событийная платформа — основной способ интеграции; легаси на критическом пути отсутствует.

## Мониторинг и эскалация

| Метрика | Порог эскалации | Владелец |
|---------|-----------------|----------|
| % интеграций через event mesh | < плана на квартал | Enterprise Architect |
| Lag потоковых витрин | > 15 мин для KPI | Data Platform Lead |
| Инциденты PHI/PCI в аналитике | > 0 | CISO |
| Расхождение KPI old BI vs portal | > 2% | Domain Data Owner |
| Размер DLQ | рост > 24 ч без разбора | SRE / Platform |

**Ритм:** ежемесячный Risk Review, ежеквартальный пересмотр карты рисков, эскалация критических рисков на Steering Committee.

## Резервные сценарии (contingency)

| Если срабатывает риск | Действие |
|-----------------------|----------|
| T1 — критические ошибки миграции DWH | Заморозить cutover домена, откат на read-replica DWH, увеличить срок ACL |
| T2 — простой клиник | Немедленный rollback на PowerBuilder-интерфейс (временный), post-mortem за 48 ч |
| O2 — нехватка кадров | Приоритизация 1 домена, временное усиление аутстаффом, сдвиг этапа 3 на 6 мес. |
| A4 / T3 — утечка данных | Изоляция компонента, отзыв ключей, уведомление регулятора по процедуре |
