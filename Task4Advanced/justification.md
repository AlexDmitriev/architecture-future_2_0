# Обоснование событийного подхода vs Camel ESB и DWH

## Текущее состояние (AS-IS)

В данный момент интеграции построены вокруг:

-   **Монолитного DWH (SQL Server 2008)** — хранилище и одновременно вычислительный слой с бизнес-логикой.
-   **Apache Camel ESB** — синхронные и batch-маршруты между финтехом, AI, клиниками и внутренними сервисами.
-   **Power BI / PowerBuilder** — потребители данных из DWH.

### Проблемы текущей модели

| Проблема | Проявление в бизнесе |
| --- | --- |
| **Связанность через центр** | Любое новое направление (фарма, оборудование) требует доработки DWH и маршрутов Camel |
| **Batch-латентность** | Отчёты формируются часами; нет near-real-time KPI |
| **Масштабирование** | Сотни ТБ и множество трансформаций перегружают один DWH |
| **Time-to-market** | Запуск финтех- или AI-фичи блокируется очередью на ETL/ESB |
| **Регуляторика** | Смешение PHI, PCI и аналитики в одном хранилище повышает риск утечек |
| **Эволюция** | SQL Server 2008 и PowerBuilder — тупиковая ветка для найма и поддержки |

---

## Целевой подход (TO-BE): домены + события

Каждый bounded context владеет своими данными и публикует **факты** (domain events). Потребители подписываются асинхронно. DWH и Camel остаются только как **временные мосты** (CDC, ACL) на период миграции.

---

## Преимущества

### 1\. Гибкость и независимость доменов

**Было:** финтех-сервис (Go/Java) и AI (Python) синхронно ходят в ESB → DWH; схема общая, релизы согласуются неделями.

**Стало:** Lending публикует `CreditAgreementCreated`; Analytics, Banking и уведомления подписываются независимо. Новый партнёр (фарма) подключается подпиской на `PartnerOrderPlaced` без изменения кода клиник.

> DDD bounded contexts позволяют развивать медицину, банк и AI отдельными командами с собственным ритмом релизов.

### 2\. Масштабируемость

**Было:** один DWH — узкое горлышко для записи и чтения; пиковые нагрузки (отчётный день, массовые исследования) деградируют все системы.

**Стало:**

-   Горизонтальное масштабирование Kafka и stream processors.
-   Доменные БД масштабируются независимо.
-   Analytics строит проекции из потока событий, не нагружая операционные OLTP.

При выходе в 2–3 региона события реплицируются с учётом data residency; не нужно клонировать весь DWH.

### 3\. Скорость реакции (near-real-time)

**Было:** ETL в DWH → отчёт в Power BI: задержка часы.

**Стало:**

-   `DiagnosticStudyCompleted` → Medical AI запускает анализ за секунды.
-   `PaymentReceived` → Billing и Lending обновляют статусы без ночного batch.
-   Витрина самообслуживания читает материализованные проекции с lag в минутах, не часах.

Это критично для монетизации AI и финтех-сервисов «в моменте» (кредит на лечение сразу после приёма).

### 4\. Безопасность и соответствие регуляторам

**Было:** медкарты, кредиты и KPI в одном DWH; сложно гарантировать, что витрина не получит PHI.

**Стало:**

-   События в аналитику — без PHI (только ID и агрегаты).
-   Medical AI получает `dataRef`, не полную карту.
-   Политики на уровне топиков и Schema Registry.

### 5\. Подключение новых бизнес-направлений

Планируемые фармацевтические компании и производитель оборудования интегрируются через **Partner Commerce** и события `PartnerOrderPlaced` / `InventoryReserved`, без переписывания ESB-маршрутов и stored procedures в DWH.

### 6\. Наблюдаемость и устойчивость

-   DLQ и replay для «ядовитых» сообщений (вместо тихого падения ESB-роута).
-   Event sourcing trail для аудита (важно для банковской лицензии).
-   Идемпотентные consumer’ы — устойчивость к повторной доставке.

## Сравнение: Camel + DWH vs Event-Driven

| Критерий | Camel ESB + DWH | Событийная платформа |
| --- | --- | --- |
| Связность | Высокая (hub-and-spoke) | Низкая (pub/sub) |
| Латентность интеграции | Минуты–часы (batch) | Секунды–минуты |
| Добавление потребителя | Менять маршрут/ETL | Новая подписка |
| Масштаб данных | Вертикальный рост DWH | Горизонтальный sharding + lake |
| Версионирование контрактов | Неявное (сломанные JOIN) | Schema Registry |
| Отказоустойчивость | ESB — SPOF | Партиции, репликация Kafka |
| Стоимость изменений | Высокая (регресс по всему DWH) | Локальная в домене |

---

## Почему не оставить Camel, добавив Kafka?

Частичная модернизация без DDD приводит к **dual write**: данные и в DWH, и в Kafka, с расхождениями. Правильный путь:

1.  **0–6 мес.:** CDC из DWH → события (мост); пилот в 1–2 доменах.
2.  **6–18 мес.:** новые фичи только через события; Camel — ACL для легаси.
3.  **18–36 мес.:** DWH read-only → decommission; Camel снят с критического пути.

## Риски событийного подхода (и почему выгоды перевешивают)

| Риск | Митигация |
| --- | --- |
| Сложность распределённых систем | Пилот, Schema Registry, стандарты событий |
| Eventual consistency | Согласованные UX (статусы, уведомления) |
| Дублирование проекций | Data Mesh + владельцы data products |

Для компании с **четырьмя подразделениями**, планами **гео-расширения** и **сотнями ТБ** событийная архитектура — не опция «для моды», а способ снять структурный потолок монолитного DWH и ускорить time-to-market без компромисса по регуляторике.

## Вывод

Переход на интеграцию через доменные события даёт:

1.  **Гибкость** — автономные команды и быстрое подключение партнёров.
2.  **Масштабируемость** — независимый рост доменов и регионов.
3.  **Скорость** — near-real-time вместо batch-цепочек Camel → DWH → BI.
4.  **Безопасность** — явные границы PHI/PCI и контролируемые контракты.

Camel и DWH остаются только как **мосты совместимости** на время миграции, а не как целевая модель интеграции.
