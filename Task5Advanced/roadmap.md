# Стратегический роадмап Data Mesh

**Компания:** «Будущее 2.0»  
**Горизонт:** 36 месяцев  
**Связь с бизнес-целями:** продукты, география, near-real-time данные

---

## Ключевые роли

| Роль | Зона ответственности | Подразделение |
| --- | --- | --- |
| **Владелец data product (Data Product Owner)** | Бэклог витрин домена, качество KPI, приоритеты | Домен (финтех / клиники / ИИ) |
| **Инженер данных (Data Engineer)** | Пайплайны, события → витрины, контракты схем | Домен + платформа |
| **BI-аналитик** | Семантический слой, шаблоны отчётов, обучение пользователей | Головной офис + домены |
| **Инженер платформы (Platform Engineer)** | Kafka, lakehouse, CI/CD, наблюдаемость | Центральная платформа |
| **Архитектор домена** | Границы контекста, ADR, ACL к легаси | Домен |
| **Steward качества данных** | DQ-правила, каталог, lineage | Совместно домен + платформа |

---

## Этапы внедрения

### Этап 0. Подготовка (месяцы 0–2)

| Действие | Роли | Бизнес-цель |
| --- | --- | --- |
| Согласование границ доменов и ADR | Архитектор домена | Архитектура согласована (цель 2 мес.) |
| Назначение Data Product Owner в 2 пилотных доменах | Владелец data product | Ответственность за данные |
| Запуск Kafka + Schema Registry + DLQ | Инженер платформы | Основа событийной интеграции |
| FinOps и облачный landing zone | Инженер платформы | Снижение TCO миграции |

**Результат:** архитектура утверждена, пилотные домены выбраны (финрасчёты + пациентский поток).

---

### Этап 1. Пилот (месяцы 2–6)

| Действие | Роли | Бизнес-цель |
| --- | --- | --- |
| Первые data products: «Портфель кредитов», «Поток пациентов» | DPO + Data Engineer | Data Mesh Trial |
| CDC из DWH → события (Debezium) | Data Engineer, Platform | Мост без расширения DWH |
| MVP портала self-service (1 домен) | BI-аналитик | Витрина к 12 мес. |
| Обучение доменных команд контрактам событий | Platform + DPO | Единые принципы |
| KPI пилота: lag витрин < 15 мин, 0 PHI в портале | Steward | Регуляторика |

**Результат:** 2 data products в prod-like, портал MVP, exit criteria пилота выполнены.

**Привязка к бизнесу:** ускорение отчётов по кредитам и загрузке клиник.

---

### Этап 2. Масштабирование (месяцы 6–18)

| Действие | Роли | Бизнес-цель |
| --- | --- | --- |
| Data products в доменах: биллинг, ИИ-метрики, склад | DPO × 4 домена | Продуктовая линейка |
| Потоковые витрины (Flink) для KPI | Data Engineer + Platform | Near-real-time |
| Каталог данных, glossary метрик | BI-аналитик + Steward | Единые определения KPI |
| ACL для Camel/DWH, сокращение маршрутов на 50% | Архитектор домена | Вывод легаси |
| Портал self-service — все домены (без PHI) | BI-аналитик | Цель 12 мес. |
| Подготовка мультирегиона (Assess) | Platform + Архитектор | География 2–3 региона |

**Результат:** портал в prod, ≥50% интеграций через события, легаси DWH read-only.

**Привязка к бизнесу:** time-to-market финтех/мед. сервисов, монетизация AI-метрик.

---

### Этап 3. Зрелость и поддержка доменов (месяцы 18–36)

| Действие | Роли | Бизнес-цель |
| --- | --- | --- |
| Decommission DWH и Camel с критического пути | Platform + все домены | Слабосвязанная платформа |
| Региональные data products (data residency) | DPO + Platform | Выход в новые регионы |
| Партнёрские витрины (фарма, оборудование) | DPO Partner + Data Engineer | Новые B2B-источники |
| FinOps, оптимизация облака | Platform | TCO год 3–4 |
| Центр компетенций Data Mesh | BI-аналитик (лид) | Поддержка доменов |
| MLOps для AI data products | Data Engineer (ИИ) | Монетизация ИИ |

**Результат:** событийная платформа — основной способ интеграции; доменная аналитика.

**Привязка к бизнесу:** масштабирование по продуктам, географии и объёму событий.

## Риски и зависимости

| Риск | Митигация на роадмапе |
| --- | --- |
| Нехватка DPO | Назначить до этапа 1, обучение на пилоте |
| Dual-run перерасход | Жёсткий план вывода легаси на этапе 2 |
| Сопротивление BI-пользователей | Параллельная сверка отчётов (этап 2) |
| Регуляторика PHI | Steward + политика «no PHI» в портале с этапа 1 |
